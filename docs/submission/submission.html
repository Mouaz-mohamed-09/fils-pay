1. Summary

What we found. 53 defects across money, security, settlement, reporting and UI. Seven were critical: money lost or another merchant reachable (refunding anyone's payment, logging in without the OTP or into another merchant, a payment link charged twice, payouts computed in float32, the balance button wiping a merchant to 7K, and refunded sales still paid out in full).

What we fixed. All 53, each with the smallest change and a new test or reproduction (none of the existing locked tests edited, the audited packages/money untouched). We finished FP-300 (refunds) end to end: API, ledger, cumulative fee reversal, settlement netting, signed webhook, timeline, reports and reconciliation. We deployed on Dilmune Cloud within the 1 vCPU / 2 GB budget, with load shedding, restart on crash and a one-command git deploy.

What we left alone. Five locked tests that assert the bugs finance reported (CSV 0.475, the 245 bps display): fixes kept, tests not edited. The March sweep postings already in production (need finance sign-off to reverse). Real OTP delivery (needs an email/SMS provider).

Main root cause. Safeguards that existed only on paper. ADRs, comments and CLAUDE.md asserted protections the code didn't have: a unique index, a dedupe table, a read-only role, integer money, a safe seed. Several of those claims were earlier AI answers nobody checked. Each one hid a bug that we found by reading the schema, running the system, or load-testing it.

Not interrupting a settlement run. (1) deploy.sh refuses between 00:00 and 01:00 Bahrain time, the close window (override FORCE=1). (2) Settlement gets a 2-minute stop grace period: on SIGTERM the daemon cancels its context and the in-flight batch transaction commits or rolls back. (3) Every batch is one transaction and CloseBatch/PayoutBatch are idempotent, so a cut-short batch is redone on the next tick, never half-applied. (4) Compose recreates only changed services; Postgres is not restarted by a code deploy.

3. Capacity

Estimate: about 10 checkouts/s sustained (≈30 requests/s) with every response correct; ceiling about 16 checkouts/s. Beyond it, excess requests get an immediate 503 and accepted payments stay correct.

Our load test

Tool: k6 0.54 (ops/load/checkout.js). Method: ramping arrival rate, 15 s ramp then 45 s hold; one iteration = merchant creates a payment link → buyer opens it → buyer pays (authorize + capture), run over the internet against the live server. The simulated acquirer keeps its defaults (100–400 ms per call, ~2% failures); its 402/502 answers are counted as correct, not as server errors.

Bottleneck

First the ledger: every checkout did full-table scans (balance trigger on an unindexed column: 27,430 sequential scans, 376 M rows). Indexes (R1) cut pay p95 at 30/s on the tuning machine from 3.35 s to 780 ms. Now: Postgres CPU (it reaches its 0.35 vCPU cap at ~20/s; the API uses ~0.2 of its 0.5) and the connection pool, which each pay holds through two acquirer calls (25 connections / ~0.55 s ≈ 45 pays/s upper bound).

Turning away excess and recovering

Admission control (plugins/loadShedding.ts): past 64 requests in flight the API answers 503 Retry-After: 1 at once. Caddy fails fast (2 s) while the API restarts. Crash test: at 60/s we ran kill -9 on the API; Docker restarted it within seconds and the audit afterwards found 0 unbalanced ledger groups, 0 paid links without a capture, 0 stuck idempotency keys and 0 double charges (after fixing R2, which the first crash test exposed).

Root causes

Floats and double rounding on money

Money stored as integer fils (ADR-0001) but converted to floats or rounded twice on the way. M1, M4, M5, M9, M10, M11, F4

Two sources of truth for one rule

The same figure (balance, rate, fee) computed by different code from different data, so they drift. M6, M7, M8, M12, O1, M2

Check-then-act without atomicity

Read, decide, then write in separate steps; concurrent requests all pass the check. S3, F3, O3, S11, M3, S6, R2

Missing tenant scope

Queries keyed by an ID from the request instead of the merchant from the session. S1, S2, S4, F1, F2, S16

Documented safeguards that never existed

Comments, ADRs and CLAUDE.md asserted protections (indexes, triggers, read-only roles, safe seeds) that the code did not implement; earlier unchecked AI answers were part of this. S7, S8, S9, S10, S12, S13, S14, S15, S17, O2

Unfinished feature and untested runtime

FP-300 helpers never wired; the stack had never been run end to end, so integration bugs hid. F5, F6, F7, F8, F9, R1, R3, R4, R5, R6, R7, R8, R9, R10, O4, O5
